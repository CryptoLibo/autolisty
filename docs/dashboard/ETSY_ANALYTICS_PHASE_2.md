# Dashboard Phase 2: Etsy catalog

The existing Etsy OAuth connection requests `shops_r`, `listings_r`, and `listings_w` in `lib/etsy/auth.ts`. No scope changes are made here. The owner-only manual sync uses `GET /v3/application/users/{user_id}/shops` through the existing primary-shop helper, followed by `GET /v3/application/shops/{shop_id}/listings` for `active`, `draft`, and `inactive` states. There are no commercial mutations.

`GET /api/dashboard/etsy` reads the Automation SQLite cache only. `POST /api/dashboard/etsy/sync` refreshes it at most once per 15 minutes. It requests pages sequentially, capped at ten pages per state. The counts come from Etsy's `count`; if details exceed the cap, the status is `partial` and period creation counts are suppressed. A provider failure preserves the last successful snapshot and exposes only a classified error code. The token stays in the existing httpOnly cookie; neither token nor raw Etsy response is stored in this cache or returned by these routes. Only the first connected shop is represented, as elsewhere in the current integration.

Migration v11 adds `dashboard_etsy_sync` and `dashboard_etsy_listings` to the existing Automation SQLite database. It runs on normal startup and does not recreate or clear existing tables. Before deployment, back up the production Automation SQLite database using its existing backup procedure. No new environment variable is needed. `AUTOMATION_DB_PATH` and the existing Etsy OAuth settings remain required.

The Dashboard displays live-sourced active, draft, and inactive listing counts after a successful manual sync; up to 12 recent listing identifiers, titles, states, and prices; and listings **created**, not published, during 7/30/90 days when the full catalog was captured. The catalog status and last successful sync time are shown. Historical catalog evolution begins only after multiple snapshots are implemented; it is not inferred from the current snapshot.

Orders, completed/canceled orders, sales, gross/net revenue, average order value, product sales, fees, refunds, and trends remain pending. Reading receipts requires `transactions_r`, which the current OAuth token does not have. Before adding those metrics, request that scope and explicitly reauthorize the owner's Etsy connection, then verify available receipt fields and financial semantics. Visits, conversion, Ads and Pinterest analytics also remain pending; no values are estimated. CSV imports may later fill gaps such as fees and expenses, subject to provenance and reconciliation.

To validate after deployment: confirm the logo on each module, open Dashboard and verify that it does not trigger Etsy catalog requests, click **Sincronizar Etsy** as the owner, verify counts and timestamp, switch periods, and verify that orders/revenue remain `--`. Repeated clicks within 15 minutes should be blocked. If sync fails, the last successful snapshot should remain visible. Revert the code to the prior commit to disable the UI and endpoints; migration v11 tables can be left in place without affecting older code. Do not drop the tables or database during rollback.
